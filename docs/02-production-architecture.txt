PROFILI — PRODUCTION INFRASTRUCTURE
===================================
Audience: real concurrent users, resumes in parallel, live voice, transcripts, analytics.
This is the same domain model as local (see 01-local-architecture.txt).
Only the hosts, isolation, and traffic patterns change.


1. PRODUCT FLOW (PRODUCTION)
----------------------------
  Signup / login
  Upload resume (direct to object storage)
  Parse + extract (async workers)
  Build voice agent (async workers)
  Recruiter talks (OpenAI Realtime stream, ephemeral session)
  Persist transcript during the call
  Analyze after hangup
  Owner sees Insights

Hard split of paths:

  EDGE / SYNC        auth, presign, status, mint session, read insights
  JOBS / ASYNC       parse, embed, compile agent, analyze
  MEDIA / REALTIME   browser <-> OpenAI. Your servers do not mix this with PDF parse.

3. HOW CONCURRENT RESUME UPLOADS WORK
-------------------------------------
Problem: 200 users drop PDFs at once. Node cannot parse 200 PDFs in request handlers.

Pattern: direct-to-S3 + queue. Next.js never holds the bytes.

  A. Client asks for a slot
     POST /api/resumes
     body: { fileName, contentType, bytes }
     checks: auth, plan quota, 10 MB cap, application/pdf, per-user rate limit

  B. API writes a row (status=uploaded) + outbox in one DB transaction
     returns presigned PUT (15-60s, single object, SSE enforced, Content-Type locked)

  C. Browser uploads to S3/R2 in parallel. Your app CPU stays idle.
     Use multipart only above ~20 MB. Resume PDFs should not need it.

  D. Client calls complete
     POST /api/resumes/:id/complete
     API HeadObject: exists, bytes match, content-type match
     enqueue resume.parse.requested

  E. Parse workers
     consumer group on profili.jobs.parse
     autoscale: 1 worker per ~4 in-flight OpenAI extract calls
     each worker process: p-limit 4 LLM calls, 1 CPU-bound extract

Backpressure:
  - If parse queue depth > 200, complete() still 200s, UI shows "in queue, position N"
  - Do not 500 the uploader because workers are slow
  - Per-user: only 1 parse + 1 agent build in flight (advisory lock on user_id)
  - Global: Redis max stream length (MAXLEN ~ 100k) plus DLQ

S3 settings:
  - private buckets, Block Public Access
  - SSE-S3 or SSE-KMS
  - lifecycle: abort incomplete multipart 1 day
  - optional: S3 Object Created event as a backup trigger if complete() never arrives
    (reconcile job: uploaded rows older than 2 min with object present -> enqueue parse)

This last reconcile is how you survive "user closed the tab after PUT".


4. PARSE AT PRODUCTION LOAD
---------------------------
Hot path inside parse-worker:

  download PDF (stream, not full buffer if large)
  text extract in a child process / wasm (crash isolation)
  if extracted chars < threshold, mark needs_ocr and fail v1 with a clear error
      (OCR is a later queue, do not block the main parse pool)
  LLM extract JSON (strict schema, retry 2x)
  embed chunks in batches of 64
  write parsed_resumes + resume_chunks
  emit resume.parsed + agent.build.requested

Timeouts:
  extract: 30s
  llm: 45s
  embed: 30s
  whole job: 3 min then fail + user-visible error

Idempotency key: parse:{resume_id}:{sha256}
Re-upload of the same bytes should reuse parsed_resumes and skip LLM.


5. MAKING THE AGENT READY (BEYOND OPENAI STREAM)
------------------------------------------------
You already know the call itself is OpenAI Realtime.
The work BEFORE the first recruiter shows up is what "agent ready" means.

Build pipeline (agent-worker):

  1. Load ResumeDocument
  2. Compile facts_card (small, always in the prompt)
  3. Compile instructions (persona + honesty rules + language)
  4. Attach tools that hit YOUR api, not OpenAI memory:
       search_resume(query)     -- pgvector
       get_role_timeline()
       get_project(name)
     Realtime model will call these during the conversation.
     This is the main quality lever besides the prompt.
  5. Store realtime_config jsonb:
       model, voice, turn_detection.server_vad,
       input_audio_transcription.model = whisper-1,
       instructions, tools, temperature
  6. Bump agent_versions, set agents.status = ready

What else besides the stream:

  - Ephemeral client secrets, 60s TTL, minted per talk session. Never ship OPENAI_API_KEY to the browser.
  - One OpenAI Realtime session per live call, not per agent. Idle agents cost $0.
  - Versioned agents: a live call pins agent_version so a rebuild mid-call cannot change the persona.
  - Warmth: none. Do not pre-open sockets.
  - Fallback: if Realtime is down, talk page stays up with "voice temporarily unavailable".
    Agent status stays ready. Voice outage is not a parse failure.
  - Prompt cache / prefix: keep the first N tokens of instructions stable so OpenAI can cache.
    Put volatile bits (today's date, visitor company if known) at the end.
  - Eval set: 20 golden questions per seed resume. Run after each prompt change.
    Block promote if "invented employer" rate > 0.

Optional later (not v1):
  - Fine-tuned small model for tool-calling
  - Clone-ish TTS (you are not doing this now)
  - Server voice-gateway to record raw audio for compliance


6. CONCURRENT LIVE CALLS
------------------------
Each recruiter:

  POST /api/talk/:handle/session
    rate limit by IP + by agent
    insert calls (status=live, agent_version pinned)
    create OpenAI realtime session (server-side)
    return { callId, clientSecret, realtimeConfig public bits }

  Browser connects to OpenAI directly.

  Transcript deltas POST to /api/calls/:id/events in small batches
    verify call is live, seq is monotonic, payload < 32 KB
    insert transcript_turns (on conflict seq do nothing)

  Hangup: POST /api/calls/:id/end
    set ended_at, duration_s
    enqueue analysis.requested

Capacity:
  Your Next instances only handle JSON. 1 small instance can take thousands of event posts.
  OpenAI is the media bottleneck and the bill.
  Limit concurrent live calls per agent (example: 5) so one viral link cannot empty your quota.
  Global semaphore in Redis: realtime:live with MAX from billing.

Do not run analysis on each turn. That will add lag and cost. Analysis is an after-call job.


7. TRANSCRIPTION
----------------
Primary: OpenAI Realtime input_audio_transcription + assistant text items.
Store as transcript_turns while the call is live so the owner can open a still-running call.

Secondary (repair job, optional):
  If you later add a voice-gateway and store audio in S3,
  a whisper-repair worker can replace low-confidence turns.
  Mark source=whisper_repair. Keep the original row.

Never block call.ended on repair. Analyze on the live transcript first.
If repair finishes, you may enqueue analysis again with idempotency analysis:{call_id}:v2.


8. ANALYTICS
------------
analysis-worker, queue profili.jobs.analyze, lower priority than parse/agent.

Input: full transcript + facts_card + skills list
Output: analyses.report jsonb (see local doc)

Rollups for Insights (materialized, refresh every 1 min or on analysis.ready):

  insight_daily
    agent_id, day, calls, avg_duration_s, top_questions jsonb, skills_coverage jsonb

Queries the Insights UI needs (fast):
  last 20 calls for agent
  counts today / 7d
  most asked topics
  questions that were "no" or "partial" (agent gaps — feed back into rebuild)

Do not make the Insights page scan transcript_turns for every load.
That table grows fast. Roll up.


9. PRODUCTION DATA STORES
-------------------------
Postgres (Neon or RDS Postgres 16 + pgvector)
  - primary
  - connection pooler (PgBouncer / Neon pooler) in front of Next AND workers
  - Next uses pooled URL; workers use pooled URL; migrations use direct URL
  - row-level: every owner query filters user_id from the session. Do not skip this.

Redis
  - Streams for jobs (or SQS if you want infinite buffer and less Redis ops)
  - rate limits
  - live call counters
  - short cache: public agent card by handle (30s)

Recommendation:
  Stay on Redis Streams until job volume is large and you want per-queue isolation,
  then move jobs to SQS + keep Redis for rate limits. Wrap behind a Queue interface
  so workers do not care.

Object storage
  - Cloudflare R2 (no egress) or S3
  - same keys as local MinIO
  - presign only, no public resumes

Secrets
  - platform secret store, not .env on disk
  - OPENAI_API_KEY only on server + workers
  - separate keys for parse vs realtime if OpenAI lets you project-split later


10. SCHEMA (SAME AS LOCAL, PRODUCTION NOTES)
--------------------------------------------
Tables: users, sessions, resumes, parsed_resumes, resume_chunks,
        agents, agent_versions, visitors, calls, transcript_turns,
        analyses, outbox, processed_jobs, insight_daily

Extra production columns:

  users.plan, users.stripe_customer_id
  resumes.sha256 unique per user (dedupe)
  calls.agent_version int not null
  calls.ended_reason  text          -- hangup|timeout|error|rate_limit
  transcript_turns.confidence real
  agents.live_calls_limit int default 5

Partitioning (when you have volume, not on day one):
  transcript_turns PARTITION BY RANGE (started_at) monthly
  calls PARTITION BY RANGE (started_at) monthly

Do not partition until a table is tens of millions of rows.

Indexes that matter under concurrency:
  calls (agent_id, started_at desc)
  transcript_turns (call_id, seq)
  outbox partial (published_at is null)
  resumes (user_id, status)
  agents (handle) unique

Migrations: expand/contract. Add columns nullable, backfill, then constrain.


11. AUTH IN PRODUCTION
----------------------
  Email + password (argon2id) for v1, session cookie
  Optional later: Google OAuth, magic link
  CSRF: SameSite=Lax cookie + origin check on POST
  Public talk routes are unauthenticated but rate-limited
  Owner APIs require session

Do not put JWT in localStorage. Cookie session, rotate on login.


12. WORKER PLATFORM
-------------------
Run workers as a separate service from Next (same image, different CMD).

Autoscale on queue depth:
  parse-worker   min 1  max 20   scale when stream lag > 25
  agent-worker   min 1  max 10
  analyze-worker min 1  max 10   scale slower, cheaper model
  outbox-pub     min 1  max 2    (singleton-ish; two is ok with skip locked)

Health:
  /healthz on Next (db ping, redis ping)
  workers: if they cannot XREADGROUP for 30s, fail the probe

Deploys:
  Next and workers can roll independently
  Agent instruction format is versioned in jsonb schema_version
  Old workers must no-op unknown jobs, not crash


13. OPENAI USAGE AND COST CONTROL
---------------------------------
  Parse + extract: gpt-4o-mini, JSON schema
  Embeddings: text-embedding-3-small, batch
  Realtime: only while call.status=live
  Analysis: gpt-4o-mini, after hangup, skip calls < 20s

  Per-user monthly token budget in Redis, hard stop with a billed error
  Log usage_events (user_id, kind, tokens, cost_est) for your own billing later


14. RELIABILITY
---------------
  Outbox + consumer groups (see local doc)
  SQS delay / Redis retry with backoff: 5s, 30s, 2m, then DLQ
  Poison PDF: after 5 fails, resumes.status=failed, email/in-app
  Idempotent complete() and end()
  At-least-once transcript events: unique (call_id, seq)
  DB transactions: row + outbox together, always
  Multi-AZ postgres
  Object storage 11 nines, you still backup parsed JSON to postgres (already there)


15. SECURITY
------------
  Presigned PUT: exact key, exact content-type, max bytes
  Magic-byte sniff on parse-worker (PDF header) before extract
  ClamAV or an S3 malware scan hop if you allow arbitrary PDFs at scale
  Strip PDF JS / launch actions if you ever render pages
  Hash visitor IPs, do not store raw
  RLS or always user_id = session.user_id in queries
  Public handle enumeration: generic 404, rate limit session mint
  No PII in worker logs (redact email, phone from ResumeDocument logs)


16. OBSERVABILITY
-----------------
  Traces: request_id through API -> outbox id -> job id
  Metrics:
    upload_complete_total
    parse_seconds (p50/p95)
    agent_ready_seconds (upload complete -> ready)
    realtime_session_mint_total / errors
    live_calls
    analysis_seconds
    outbox_lag
    openai_errors by endpoint
  Alerts:
    parse p95 > 90s
    outbox lag > 50 for 5 min
    realtime mint error rate > 5%
    worker memory / restarts
    postgres connections near cap


17. ROLLOUT VS CURRENT DEMO
---------------------------
  Phase 0  keep UI, this doc
  Phase 1  postgres + auth + presign + MinIO/S3, still mock parse
  Phase 2  parse-worker + agent-worker, talk still mocked
  Phase 3  OpenAI Realtime on /talk/[handle]
  Phase 4  transcript persist + analysis-worker + Insights live
  Phase 5  quotas, malware scan, partitions, SQS if needed

Do not launch Realtime before parse/agent jobs are reliable.
A talking agent with an empty facts card is worse than a queue spinner.


18. WHAT "EXTREMELY SCALABLE" ACTUALLY MEANS HERE
-------------------------------------------------
  Uploads scale with object storage, not Next
  Parse/agent/analyze scale by adding workers
  Live voice scales with OpenAI, gated by your Redis semaphore
  Insights scale with daily rollups, not raw turn scans
  The database stays small: JSON documents + ids. Audio stays in object storage.

If you outgrow one region: pin user_id to a region, store resumes in that region's bucket,
  keep handles globally unique in one postgres. You will not need this at v1.
